# v3.0.0

**Released:** 2026-10-07
**versionCode:** 62
**Commit:** (see git log)

## What's New

### 🎯 Proactive Assistant — AI-driven rules

Transformed the rules system from a manual form (unusable) to an AI-driven system. Users now ask the AI in chat to create rules ("every morning at 7am tell me the weather") and the AI calls the new `createRule` tool automatically.

### New: 5 rule management tools (in ToolExecutor)
- **`createRule(name, triggerType, triggerValue, action, days?)`** — create a rule that fires automatically
- **`listRules()`** — list all rules with id, trigger type, days, enabled state
- **`deleteRule(id)`** — delete a rule by id
- **`modifyRule(id, name?, triggerType?, triggerValue?, action?, days?, enabled?)`** — modify an existing rule
- (toggleRule is handled via modifyRule with `enabled=false`)

### New: RuleScheduler.kt (AlarmManager-based)
- Replaces the old Handler-based polling in RuleEngine (which died when app was killed)
- Uses `AlarmManager.setExactAndAllowWhileIdle()` — fires in Doze mode, survives app kill
- Each rule gets a unique `PendingIntent` with `requestCode = rule.id.toInt()` so we can cancel individually
- `getNextFireTime()` calculates next occurrence based on day-of-week filter
- Auto-reschedules after firing (daily rules fire again tomorrow at the same time)

### New: RuleTriggerReceiver.kt
- BroadcastReceiver registered in AndroidManifest
- Receives `com.ai.agent.RULE_TRIGGER_ALARM` intents from AlarmManager
- On receive: looks up the rule by id, starts AgentService with `ACTION_PROCESS_RULE`, reschedules

### Fixed: NotificationListener broadcast → AgentService wiring
**Before:** `NotificationListener.triggerRule()` sent a broadcast `com.ai.agent.RULE_TRIGGERED` — but nothing received it. Notification rules were silently broken.

**After:** `NotificationListener.triggerRule()` starts AgentService directly with `ACTION_PROCESS_RULE` intent + extras (rule name, action, trigger type, notification title/text). AgentService picks it up via `onStartCommand` and runs `processRuleAction()`.

### New: AgentService.processRuleAction() — full agent loop for rules
**Before:** Rules used `processVoiceCommand()` which has a simplified system prompt (dumber LLM context).

**After:** Rules use a new `processRuleAction()` that uses the FULL system prompt (same as chat agent loop) + a context block explaining:
- Which rule fired
- What triggered it (notification title/text if applicable)
- That the user isn't actively chatting — execute efficiently, be brief

The loop runs the same iterative tool-calling pattern as the chat agent: LLM decides tools → tools execute → results fed back → repeat until task complete or max iterations.

### Rewritten: RulesActivity (clean list view)
**Before:** Manual form with trigger type dropdown, trigger value text field, action text field. Not user-friendly.

**After:** Clean list view with:
- Header: "Ask the AI in chat to create rules. Manage them here."
- Example prompts card showing common rule requests
- "Open Chat to Create Rule" button (returns to MainActivity)
- Rules list with toggle + delete per rule
- "Enable Notification Access" button (deep-links to system setting)
- "Disable Battery Optimization" button (needed for reliable Doze-mode scheduling)

No more form. Users either ask the AI in chat → AI creates the rule → it appears here.

### Database schema: added `days` column
- DB_VERSION bumped from 1 → 2
- `onUpgrade()` uses `ALTER TABLE rules ADD COLUMN days TEXT` (preserves existing data)
- `Rule` data class now has `days: String?` field — `null` means daily, `"mon,tue,wed,thu,fri"` means weekdays
- Added `updateRule()` method with nullable parameters (only updates provided fields)

### System prompt: added Rule Management section
Teaches the LLM:
- When to create a rule (vs. execute once)
- Examples of common rule requests with exact tool calls
- The 4 supported trigger types (time, notification, battery_low, charging)
- After creating a rule, tell the user what was created (name, trigger, action)

### AndroidManifest changes
- Added `<receiver>` for `RuleTriggerReceiver` with `com.ai.agent.RULE_TRIGGER_ALARM` intent filter
- Added permissions:
  - `SCHEDULE_EXACT_ALARM` (Android 12+ for exact-time alarms)
  - `USE_EXACT_ALARM` (Android 13+ alternative)
  - `RECEIVE_BOOT_COMPLETED` (for future boot-reschedule feature)

## Known Issues
- **Battery/charging triggers not yet implemented** — the tools accept the triggerType but no receivers are registered for `battery_low` or `charging`. Planned for v3.1.0.
- **Boot reschedule not implemented** — after phone reboot, rules aren't rescheduled until the app is opened. Need a BOOT_COMPLETED receiver. Planned for v3.1.0.
- **No rule execution history** — can't see "rule X last fired at 7:00am, took 12s, succeeded". Planned for v3.2.0.
- **No dry-run** — can't preview what a rule would do without waiting for the trigger. Planned for v3.2.0.
- **Rule actions run via AgentService, not MainActivity** — so the chat UI doesn't show progress while a rule executes. The TTS speaks updates, and logs are written, but the chat bubbles don't update. (This is by design — rules fire in background — but might be confusing.)

## Migration Notes
- Existing v2.4.0 users upgrading to v3.0.0 will have their DB auto-upgraded (v1 → v2): the `days` column is added with `ALTER TABLE`. Existing rules get `days = NULL` (= daily), preserving their old behavior.
- Existing rules will be rescheduled with AlarmManager on first app open (in `startRuleEngine()`).
- The old RuleEngine (Handler-based) is still running too — both systems coexist for backward compatibility. The old one is marked "legacy" in logs.
